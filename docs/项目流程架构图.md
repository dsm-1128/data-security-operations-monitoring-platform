# SecOps Agent Loop 项目流程架构图

依据日期：2026-10-17。依据当前代码、Docker Compose 配置及现有测试绘制。

本文以新版平台入口 `app.platform_app:app` 为准。旧版 `app.main:app` 是固定流程 Demo，不与新版架构混用。图中的企业模型、SSO、企业网关和 S3 表示已实现的可配置适配能力；项目默认使用模拟模型、模拟连接器与本地证据归档，真实供应商接入仍需联调。

## 1. 整体架构图

该图采用 `compose.platform.yaml` 的 MySQL + Redis + Celery 部署方式。实线表示主要调用或数据流，虚线表示可配置外部适配。

```mermaid
flowchart TB
    subgraph access[访问与身份]
        User["安全分析员 / 安全负责人 / 运维执行员<br/>审计员 / 管理员"]
        UI["安全运营工作台<br/>HTML / CSS / 原生 JavaScript"]
        Session["服务端会话<br/>组织、岗位与资产授权"]
        IdP["企业 SSO / OIDC + PKCE<br/>可配置，待真实联调"]
        User --> UI
        Session -.-> IdP
    end

    subgraph service[FastAPI 服务]
        API["平台 API<br/>告警、调查、复核、处置、导出"]
        Store["RunStore<br/>运行状态、事件与审计"]
        Action["ActionService<br/>申请、审批、执行、核对、回查"]
        Stream["SSE 事件流<br/>支持按事件 ID 续取"]
        API --> Session
        API --> Store
        API --> Action
        Store --> Stream
    end

    subgraph async[异步调查与恢复]
        Dispatch["Dispatcher<br/>投递 Outbox / 恢复过期租约"]
        Redis["Redis<br/>Celery 消息 Broker"]
        Worker["Celery Worker<br/>租约与 fencing token"]
        Loop["LangGraph Agent Loop<br/>模型决策、工具观察、完成校验"]
        Model["模型适配<br/>SimulatedModel / ModelClient"]
        Registry["只读 Tool Registry<br/>工具白名单、参数与范围校验"]
        Dispatch --> Redis --> Worker --> Loop
        Loop --> Model
        Loop --> Registry
    end

    subgraph persistence[持久化与归档]
        DB[("MySQL 8.4<br/>runs / events / outbox<br/>actions / audit / sessions")]
        Archive["证据归档<br/>共享卷，或可配置 S3<br/>SHA-256 完整性校验"]
    end

    subgraph integration[数据与处置适配]
        Read["模拟工具 / 企业只读网关<br/>资产、安全日志、认证日志<br/>业务审计、授权记录、处置手册"]
        Write["模拟处置 / 企业动作网关<br/>封禁 IP、冻结账号、状态查询"]
        LLM["外部模型 API<br/>兼容 Chat Completions tool calling"]
    end

    UI -->|HTTP 请求| API
    Stream -->|事件通知后刷新详情| UI
    Store -->|同一事务写入运行、事件、Outbox、审计| DB
    DB -->|读取未投递 Outbox| Dispatch
    Worker -->|领取运行、加载快照| DB
    Loop -->|逐步 checkpoint| DB
    DB -->|读取持久事件| Stream
    Registry --> Read
    Registry -->|校验后的结构化证据| Archive
    Action -->|处置台账、审计、原子回查关闭| DB
    Action -->|人工审批后受控调用| Write
    Model -.->|live 模式| LLM
    API -->|授权后下载与 hash 校验| Archive
```

- 调查 Agent 仅能读取证据；高风险写操作由 `ActionService` 在人工审批后发起。
- Redis 负责消息传递。运行快照、事件游标、审批与执行记录以数据库为依据。
- 本地开发也支持 `inline` 调度和 SQLite，此时由 FastAPI `BackgroundTasks` 调用同一个 `process_run()`，不经过 Dispatcher、Redis 和独立 Worker。
- `/metrics` 从数据库生成 Prometheus 格式指标；调查运行可输出 OpenTelemetry console spans。当前没有企业监控平台联调结果。

## 2. 端到端业务流程图

```mermaid
flowchart TD
    Alert["接入告警<br/>模拟场景，或真实告警 API"]
    Auth["校验身份、组织与资产权限"]
    Create["创建调查 Run<br/>queued + 事务 Outbox"]
    Queue["Dispatcher → Redis → Worker<br/>领取租约，加载已提交快照"]
    Investigate["Agent Loop 调查<br/>模型选工具 → 读取证据 → 下一轮"]
    Report["通过证据完成校验<br/>生成报告，waiting_review"]
    Attention["人工接管 needs_attention<br/>补充日志、权限或调查信息"]
    Review{"分析员 / 负责人<br/>人工复核"}
    Request["申请受控处置<br/>封禁 IP / 冻结账号"]
    Approve{"另一名负责人审批<br/>绑定参数、连接器与有效期"}
    Execute["运维执行员执行<br/>权限复查 + 幂等操作 ID"]
    Result{"外部执行结果"}
    Unknown["execution_unknown<br/>查询外部状态，禁止盲目重试"]
    Failed["已确认失败或过期<br/>继续核查，必要时重新申请"]
    Applied["applied<br/>措施已生效"]
    Verify["分析员 / 负责人回查<br/>确认仍生效、未过期并填写依据"]
    Closed["completed<br/>保留证据、轨迹、审批和审计"]

    Alert --> Auth --> Create --> Queue --> Investigate
    Investigate -->|证据充分且引用有效| Report
    Investigate -->|证据不完整、请求人工、错误或预算耗尽| Attention
    Attention -->|人工补充后 resume，重新排队| Queue
    Report --> Review
    Review -->|授权活动 / 误报，确认关闭| Closed
    Review -->|仍待核实| Attention
    Review -->|恶意活动，reviewed| Request
    Request --> Approve
    Approve -->|批准| Execute
    Approve -->|驳回后修订申请| Request
    Execute --> Result
    Result -->|已生效| Applied
    Result -->|失败| Failed
    Result -->|超时或结果未知| Unknown
    Unknown -->|仅查询并核对| Result
    Failed -->|重新申请需再次审批| Request
    Applied --> Verify
    Verify -->|回查通过，原子更新 Run 与 Action| Closed
    Verify -->|未生效、已过期或依据不满足| Failed
```

业务约束：

1. 分析员和负责人可以调查、复核与申请；负责人可以审批，运维执行员可以执行。申请人与审批人不能是同一身份。
2. 授权活动或误报在人工确认后可关闭；恶意事件必须经过处置回查关闭。待核实的事件转人工补充后继续调查。
3. 处置持续时间限制为 1–60 分钟，审批默认有效期为 30 分钟。审批过期或参数变化会阻止执行；可撤回尚未执行的申请后重新申请。
4. `executing`、`execution_unknown` 等尚未确认的动作不能通过撤回重放。回查失败本身不会自动改写 Action 状态，应先核对外部状态，确认失败或过期后再申请。
5. **Run 与 Action 是两套状态。** Run 在审批及执行期间仍为 `reviewed`；Action 单独经历 `pending → approved → executing → applied → verified`，回查成功时 Run 才变为 `completed`。

## 3. Agent Loop 内部流程图

以下是运行逻辑展开图。实际 LangGraph 由一个 `agent_step` 节点和条件自循环实现，并不是为每个图中方框单独定义一个 Graph Node。

```mermaid
flowchart TD
    Start["初始化 / 恢复状态<br/>messages、pending、evidence、预算"]
    Guard{"每步检查<br/>取消、时间预算、连续无进展"}
    Pending{"是否有待执行工具调用？"}
    ToolBudget{"工具调用预算充足？"}
    Registry["Tool Registry<br/>白名单、Schema、资产与目标校验<br/>限定时间范围，完整查询缓存去重"]
    Tool["执行只读查询<br/>模拟数据，或企业网关"]
    Evidence["校验结构化事实并归档<br/>证据 ID、查询范围、完整性与 hash"]
    Observation["写入 tool observation<br/>成功证据或可控错误，更新轨迹"]
    ModelBudget{"模型轮次 / Token 预算充足？"}
    Model["模型读取告警与历史观察<br/>返回结构化 tool calling 决策"]
    Decision{"决策类型"}
    Calls["保存 tool_calls 到 pending<br/>记录模型决策"]
    Check{"提交报告是否满足<br/>必要证据、有效引用和查询完整性？"}
    Rejected["拒绝提前结束<br/>记录缺口，要求继续调查"]
    Policy["policy_report 汇总事实<br/>规则结论 + 模型摘要"]
    Review["waiting_review<br/>交由人工复核"]
    Handoff["needs_attention<br/>请求人工处理"]
    Cancelled["cancelled<br/>停止调查"]
    Save["checkpoint 保存状态与事件<br/>校验租约和 fencing token"]
    Next{"状态仍为 running？"}
    End["结束本次运行"]

    Start --> Guard
    Guard -->|用户取消| Cancelled
    Guard -->|时间耗尽 / 连续无进展| Handoff
    Guard -->|允许继续| Pending
    Pending -->|是| ToolBudget
    ToolBudget -->|否| Handoff
    ToolBudget -->|是| Registry
    Registry -->|合法且非完整查询缓存命中| Tool
    Registry -->|参数非法 / 缓存复用| Observation
    Tool -->|成功| Evidence --> Observation
    Tool -->|连接器错误| Observation
    Pending -->|否| ModelBudget
    ModelBudget -->|否| Handoff
    ModelBudget -->|是| Model
    Model -->|调用或输出校验失败| Handoff
    Model -->|成功且 Token 未超限| Decision
    Model -->|Token 超限| Handoff
    Decision -->|tools| Calls
    Decision -->|submit_report| Check
    Decision -->|request_human| Handoff
    Check -->|不满足| Rejected
    Check -->|满足| Policy --> Review
    Calls --> Save
    Observation --> Save
    Rejected --> Save
    Review --> Save
    Handoff --> Save
    Cancelled --> Save
    Save --> Next
    Next -->|是| Guard
    Next -->|否| End
```

- 默认预算：最多 12 轮模型决策、24 次工具调用、300 秒主动运行时间、64,000 Token；可通过服务端配置调整。
- 必要证据为 `security_logs`、`business_audit`、`authorization`；账号类告警额外要求 `auth_logs`。`asset_context` 与 `playbook` 是可选调查工具。
- 模型决定下一步查询和报告摘要；最终 `verdict`、`impact`、`defense` 由 `policy_report()` 根据已校验事实生成，仍需人工复核。
- 每步结束后重新累计主动运行时间；如果本步导致超时，即使刚生成报告也会撤销报告并转人工。快照提交失败会中断执行，旧 Worker 不能继续写入。
- 默认 `SimulatedModel` 按预设策略收集证据，用于离线验收；真实 `ModelClient` 才通过外部模型动态选择工具。真实模型故障不会自动伪装成模拟成功。

## 4. 异步可靠性与恢复

1. `RunStore.create()` 在同一数据库事务写入 Run、首条事件、Outbox 和审计，避免数据库已创建但消息未记录。
2. Dispatcher 先执行 `recover_expired()`，再投递未发布 Outbox；投递完成后标记发布。重复投递可能发生，由 Worker 领取机制保证同一时刻只有有效持有者提交。
3. `process_run()` 先领取租约，取得新的 fencing token，再加载数据库快照并检查配置指纹。
4. Agent 将模型决策和工具观察分别提交为应用级快照；Worker 中断后从最后一次成功提交处继续。已完成且已提交的相同查询可复用证据。
5. 这不代表所有外部调用 exactly-once：查询完成但快照尚未提交时中断，恢复后仍可能再次查询。处置写操作另由 Action 台账和网关 `Idempotency-Key` 管理。
6. 前端通过 SSE 接收数据库持久事件，再刷新运行详情；支持 `after` 或 `Last-Event-ID` 续取，连接期间重新检查身份与资产权限。

## 5. 图中模块与源码对应

| 图中模块 | 主要源码 | 核对重点 |
| --- | --- | --- |
| 平台入口与 API | `app/platform_app.py`、`app/platform/api.py` | 创建、恢复、复核、关闭、SSE、处置与导出路由 |
| 工作台 | `app/static/platform.html`、`app/static/platform.js` | HTTP 操作、角色入口、EventSource 和详情刷新 |
| 身份与授权 | `app/platform/sessions.py`、`app/platform/auth.py` | OIDC + PKCE、服务端会话、组织/岗位/资产权限 |
| 运行与 Outbox | `app/platform/runs.py`、`app/platform/database.py` | 事务、事件、租约、fencing token 与恢复 |
| 异步调度 | `app/platform/dispatch.py`、`app/platform/worker.py` | Outbox 投递、Redis Broker 与 Worker |
| 调查装配 | `app/platform/runtime.py` | 模型/连接器选择、配置指纹、归档与 checkpoint |
| Agent 内核 | `app/agent/loop.py`、`app/agent/model.py` | 条件循环、结构化决策、预算、完成校验和人工接管 |
| 工具与证据 | `app/agent/tools.py`、`app/agent/evidence.py` | 查询范围、事实 Schema、证据完整性与规则结论 |
| 处置与网关 | `app/platform/execution.py`、`app/platform/connectors.py` | 审批绑定、幂等执行、未知结果核对与回查关闭 |
| 归档与观测 | `app/platform/evidence.py`、`app/platform/telemetry.py` | 本地/S3 归档、hash、数据库指标与 OTel spans |
| 容器部署 | `compose.platform.yaml` | MySQL、Redis、迁移、API、Worker、Dispatcher 与共享卷 |

范围说明：当前是单个调查 Agent 的多轮工具循环；代码未使用多 Agent 协作、RAG、向量数据库或 MCP 调度。真实企业接入的验证边界见 [平台交付与验证记录](platform-verification.md)。
